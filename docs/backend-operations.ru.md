# Backend публичной демо-версии: эксплуатация и оставшиеся внешние настройки

## Реализовано

- Мультикомпанийные аккаунты, роли, CSRF, одноразовые приглашения, свои знания и шаблоны.
- Формы и входящий API с маршрутизацией и защитой от дублей; платный AI не запускается от входящего сообщения автоматически.
- OpenAI-агент с инструментами, настоящие embeddings, цитаты, отдельная проверка и обязательное решение сотрудника.
- Однократный бюджет $5 на аккаунт, атомарные резервы, учёт индексации и генерации, отметки будущего запуска покупки и явный отказ от email.
- Постоянная почтовая очередь: задания сохраняются до отправки, повторы с задержкой, восстановление просроченного захвата, ограничение числа попыток, безопасные статусы пользователю.
- Единый worker для почты и индексации, heartbeat, healthcheck и очистка только устаревших технических записей.
- Ограниченные повторы индексации с задержкой, защита от старого процесса, отдельное состояние blocked для отсутствующего ключа/доступа/бюджета. Семантический поиск PostgreSQL загружает ограниченный набор кандидатов, а не весь корпус в память.
- Команда сверки неизвестных расходов с записью в аудит. Самостоятельный возврат AI-бюджета через клиентский API не допускается.
- Экспорт данных аккаунта, учёт запросов удаления для проверки оператором и экспорт рабочей области владельцем. Запрос удаления не стирает общие записи компании автоматически.
- Миграции приложения и LangGraph checkpoints отдельной командой; production API проверяет схему и не выполняет CREATE/ALTER при старте.
- Согласованные локальные SQLite backup после остановки API/worker, контрольные суммы, integrity/FK-проверка и пробное восстановление в отдельную папку.
- Compose, Helm, AWS task, CI и локальный dev-запуск учитывают worker и миграции.

Это подготовленный backend демо-продукта. Фактическая работа внешних сервисов, пригодность юридических условий и качество на данных клиентов требуют отдельной приёмки.

## Запуск

```bash
python -m scripts.migrate
python -m scripts.dev
```

Dev-команда ждёт readiness API, затем запускает worker; завершение останавливает дочерние процессы. Для сервера используются отдельные процессы API и `python -m scripts.worker`. Старый `scripts.index_worker` сохранён как совместимый вход в тот же worker. Compose/Helm/AWS уже включают его.

`python -m scripts.migrate` создаёт и обновляет как бизнес-таблицы, так и checkpoint-таблицы. Простого `alembic upgrade head` недостаточно для первой подготовки checkpoints. Production API с неподготовленной схемой откажется стартовать. Для миграций нужны отдельные DDL-права; API/worker должны использовать ограниченный runtime-доступ. Шаблон для отдельной PostgreSQL-БД: `infra/sql/runtime-role.sql`. Пароль runtime-роли задаётся оператором через безопасный DB-workflow и хранится в секретах, не в SQL/Git. Облачный blueprint пока использует первоначальную provisioning-role до настройки отдельных runtime credentials; это нужно изменить при реальном размещении.

## Проверки готовности

```bash
python -m scripts.check_backend
python -m scripts.check_backend --production
python -m scripts.check_email
python -m scripts.check_email --connect
```

Первые три команды не вызывают внешние сервисы. Код 2 означает незавершённую конфигурацию, а не автоматически поломку кода. Последняя проверяет SMTP TLS/LOGIN/NOOP без отправки письма. HTTP `/health/ready` проверяет БД/схему/checkpoints; `/health/worker` — свежий heartbeat. В Settings → Background jobs видны состояния текущей рабочей области и своих писем. Чужие письма и чужие балансы не раскрываются.

Нельзя считать SMTP-доставку подтверждённой только по `ready=true` или успешному LOGIN: получатель должен проверить реальное письмо и ссылку. Публичный домен требуется в `PUBLIC_BASE_URL`; localhost-ссылка не откроется у клиента на другом устройстве.

## Почтовая очередь

В `account_email_jobs` записаны user ID, назначение verify/reset, состояние, счётчик и срок следующей попытки. Текст письма, пароль и исходный recovery token там не хранятся. Хеш одноразовой ссылки находится в `recovery_tokens`. Поддерживаются состояния pending/blocked/sending/retry/sent/failed/cancelled.

Без SMTP credentials задание остаётся blocked и не расходует попытки. После настройки и перезапуска worker продолжит доставку свежих запросов. Запрос восстановления истекает через 30 минут ожидания, подтверждение email — через 24 часа; после истечения пользователь запрашивает новое письмо. Повторный запрос сотрудника объединяется с текущим активным заданием. После нескольких отказов задание становится failed; можно запросить новое письмо в интерфейсе. Успешное использование ссылки отзывает остальные ссылки и ненужные задания того же назначения.

SMTP не обеспечивает exactly-once: при падении после принятия письма сервером, но до записи sent возможен повтор. Lease предотвращает обычный параллельный дубль, однако не исключает этот сетевой случай. Повторная ссылка безопасна и ограничена сроком. Массовые launch-письма автоматически не отправляются.

## Сверка AI-резервов

```bash
python -m scripts.reconcile_usage
python -m scripts.reconcile_usage --reservation ID --cost-usd 0.012345 --reason 'Verified provider usage report for this reservation'
```

Без `--apply` коррекции не записываются. Сначала сверь реальный отчёт провайдера; не угадывай стоимость. Для подтверждённого результата повтори ту же команду с `--apply`. Недавние незавершённые операции защищены от преждевременной сверки. Исправление выполняется транзакционно, записывает audit event и не может повторно вернуть бюджет по уже сверенной операции. Устаревший неопределённый резерв не возвращается автоматически: это мог быть оплаченный вызов. Для старых company-level записей, перенесённых до появления персонального учёта, в демо требуется отдельная проверка атрибуции владельцу; команда не угадывает такой возврат.

## Резервное копирование и восстановление

Останови API и worker, чтобы приложение и checkpoints представляли одну остановленную систему:

```bash
python -m scripts.backup create --output var/backups/RELEASE-TIMESTAMP --confirm-stopped
python -m scripts.backup verify --path var/backups/RELEASE-TIMESTAMP
python -m scripts.backup restore-check --path var/backups/RELEASE-TIMESTAMP --output var/restore-drills/RELEASE-TIMESTAMP
```

Команды не перезаписывают существующие папки и не заменяют рабочую БД. `restore-check` проверяет копию отдельно. Храни резервные копии вне исходного сервера и Git; локальная папка не заменяет удалённый backup. Для PostgreSQL нужны настроенные managed backups/pg_dump и отдельная проверка восстановления; облачный restore не выполнялся.

## Приватность и данные

В Settings доступны экспорт своего аккаунта и запрос удаления с подтверждением текущего пароля. Оператор выгружает очередь:

```bash
python -m scripts.privacy_requests --output var/privacy-review.json
```

Команда не отправляет письма, не удаляет пользователя и не объявляет запрос выполненным. Оператор должен решить владение общими компаниями и применимые сроки хранения, затем выполнить проверенное удаление/анонимизацию. Эти решения нельзя выбрать автоматически за владельца бизнеса. JSON содержит персональные данные и создаётся с ограниченными правами доступа.

Worker удаляет только давно истёкшие сессии, старые recovery tokens, истёкшие throttle-счётчики, завершённые почтовые задания старше 30 дней и старые heartbeat. Заявки, знания, аудит решений и финансовый учёт автоматически не удаляются.

## Векторный индекс Qdrant

Реальные semantic embeddings перенесены из SQL/pgvector в отдельный Qdrant. SQL хранит аккаунты, заявки, исходные правила, финансовый учёт и реестр `vector_entries`. Миграция 006 не удаляет старые embeddings. Отдельный запуск, бесплатный перенос старого кэша, мониторинг и согласованное резервирование описаны в [qdrant.ru.md](qdrant.ru.md). SQL-backup не заменяет резервную копию Qdrant.
