# Qdrant: векторный поиск и перенос существующих embeddings

Qdrant заменяет pgvector в RAG реальных компаний. Он хранит 1536-мерные OpenAI embeddings и технические идентификаторы фрагментов. Аккаунты, компании, заявки, исходные документы, права, расходы и LangGraph checkpoints остаются в SQL: SQLite локально, PostgreSQL в существующих серверных конфигурациях. Qdrant не является заменой реляционной базы для этих данных.

## Как устроен поиск

1. Фоновая задача проверяет доступность Qdrant **до** резервирования денег и вызова модели embeddings.
2. Для нового текста создаются реальные OpenAI embeddings. Повторная попытка сначала проверяет детерминированные ID в Qdrant; неизменившиеся старые SQL embeddings можно скопировать бесплатно.
3. Qdrant подтверждает запись с `wait=true`. Только после подтверждения SQL сохраняет `vector_entries`: ID точки, профиль модели, модель и хеш текста. Новые векторы в SQL не дублируются.
4. Поиск передаёт Qdrant обязательные фильтры компании, профиля модели и ID актуальных документов. На поле компании создаётся tenant payload index.
5. Результаты дополнительно проверяются по SQL: компания, ID точки, текущая версия/даты, enabled и хеш текста. Текст ответа поступает из SQL-документов, а не из непроверенного payload Qdrant.
6. Ранжирование использует cosine, небольшой лексический бонус и MMR; агент и отдельный проверяющий продолжают работу с прежними ограничениями бюджета.

При недоступности Qdrant агент передаёт заявку человеку. Ручные операции и SQL-readiness остаются доступны. Скрытого перехода на pgvector или искусственные embeddings нет. Старый synthetic sample сохраняет отдельный hash/extractive baseline; исторические pgvector-колонки оставлены для совместимости миграций и переноса, а не для нового semantic RAG.

## Локальный запуск

Нужен работающий Docker Desktop. Для отдельного Qdrant рядом с Python-приложением:

```bash
docker compose --env-file /dev/null -f compose.qdrant.yaml up -d
python -m scripts.dev
```

Отдельный compose не читает `.env`: в нём нет интерполяции настроек. Данные сохраняются в именованном Docker volume; порт 6333 опубликован только на `127.0.0.1`. Этот локальный сервер не требует API key и не должен публиковаться в интернете.

По умолчанию приложение использует:

```dotenv
QDRANT_URL=http://127.0.0.1:6333
QDRANT_COLLECTION=supportops
QDRANT_TIMEOUT_SECONDS=10
```

Фактическое имя коллекции — префикс плюс часть профиля. Профиль включает embedding endpoint, модель, размерность, версию формата и логический префикс коллекции. Адрес физического Qdrant-сервера не входит в профиль: согласованную копию можно восстановить на другой машине без повторной оплаты embeddings.

Обычный `compose.yaml` включает собственный Qdrant **без публикации портов** и передаёт API/worker внутренний адрес `http://qdrant:6333`. Это конфигурация разработки с демонстрационными SQL-паролями, не готовый публичный production-запуск.

## Безопасный перенос существующего индекса

Миграция 006 создаёт `vector_entries`, не удаляя старые SQL embeddings или бизнес-данные. Сначала останови API и worker и сделай согласованную копию SQL и checkpoint-хранилища. Запусти Qdrant, примени миграцию, проверь перенос без записи:

```bash
python -m scripts.migrate
python -m scripts.transfer_vectors
```

После проверки счётчиков:

```bash
python -m scripts.transfer_vectors --apply --confirm-stopped
```

Команда не вызывает OpenAI и никогда не генерирует недостающие embeddings. Она переносит только источники с полным подходящим старым кэшем. `sources_without_complete_legacy_vectors` — источники, которые требуют отдельной индексации владельцем через интерфейс. Для них применяются обычные AI-бюджеты. После переноса запусти API и worker и проверь собственную заявку.

При `vector_store_unavailable` восстанови сервис; при `vector_store_auth_failed` проверь серверные права; при `vector_index_missing` восстанови согласованную копию Qdrant или явно запусти переиндексацию. Не удаляй старый кэш до проверенного восстановления.

## Oracle и другие серверы

На Oracle A1 Qdrant можно запускать в отдельном контейнере с постоянным volume. Образ `qdrant/qdrant:v1.19.0` проверен локально на ARM64. Сам Oracle-аккаунт и сервер в этом проекте не создавались.

- API и worker должны видеть один Qdrant и одинаковый префикс коллекций.
- Если Qdrant и API находятся в общей приватной Docker-сети, не публикуй порты 6333/6334 на внешнем интерфейсе и не открывай их в OCI ingress.
- Для подключения к удалённому Qdrant настрой HTTPS и `QDRANT_API_KEY` в серверном хранилище секретов. Ключ не попадает в браузер или репозиторий.
- Для постоянного диска используй поддерживаемое блочное хранилище/POSIX filesystem. Не храни Qdrant на эфемерном диске Fargate.
- Делай отдельные Qdrant snapshots и копии SQL/checkpoints. SQL-backup сам по себе не содержит новые векторы. Проверяй восстановление в отдельной коллекции/среде; при смене embedding-модели нужна переиндексация.
- В AWS Terraform добавлены URL и ARN секрета внешнего Qdrant. Постоянный Qdrant-сервер этим Terraform автоматически не создаётся; его ресурсы и стоимость считаются отдельно.
- Helm использует внешний Qdrant через существующий Secret; пример — `.env.k8s.example`.

## Проверки

`GET /health/vector` возвращает безопасный статус Qdrant; `/health/ready` проверяет SQL/schema/checkpoints, `/health/worker` — heartbeat фонового обработчика. Успешный health не доказывает полноту восстановленного индекса.

Обычные тесты используют управляемый Qdrant HTTP transport и синтетические ответы OpenAI. Для проверки настоящего сервера:

```bash
TEST_QDRANT_URL=http://127.0.0.1:6333 python -m pytest tests/test_qdrant.py
```
